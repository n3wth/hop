## 1. The three decisions the owner asked for

**Surface: a support chat embedded on `/support` — not a mode on `/ask`.**
- `/support` (static FAQ) must remain the degradation floor; mounting the chat as a flag-gated client island *above* the existing FAQ makes "LLM down → FAQ + escalation still work" mechanical rather than aspirational.
- The grounding is different: `/ask` is grounded in the destinations dataset + wanderlust voice + a2ui verdict cards; support is grounded in *hop's own behavior* (KB), *this user's account* (snapshot), and *the engine re-run* — in strict copy-spec voice. Entangling a support mode into `/api/concierge`'s already-dense stream pump (a2ui envelope, persistence, inferred facts) would grow the review surface for no reuse gain.
- What we *do* reuse: `ConciergeTransport` (parameterized endpoint), the RS-framed tool-activity protocol (`TOOL_FRAME_SEP` — already imported cross-route by the transport — plus `encodeToolFrame` and `sanitizeProse`, both already exported from `app/api/concierge/route.ts` for route-side use), and `components/ai-elements/*`. The visible tool cards ("Checked your account", "Re-ran SFO → NRT") are a large part of "impressive": the user watches the agent consult the real engine.
- **Signed-out is decided, not deferred: render the chat.** It answers how-hop-works from the KB (the marketing-adjacent win), states plainly it can't see an account and invites sign-in, never uses ownership voice ("your balances"), and escalates via the embedded `EscalationCTA` flow with a typed, `normalizeEmail`-validated address — the existing `/api/concierge-escalation` contract, unchanged.

**Tools: five, and account state is ONE tool.** `get_account_snapshot` (programs/balances, tier + alert allowance, active watches, recent alerts, booking-request statuses, home airport, AwardWallet linked y/n), `explain_verdict` (→ `verdictSummary`), `search_help` (committed KB), `transfer_paths` (→ `runTransferPaths`, zero new code), `escalate_to_human` (→ `createEscalation`, owner email via `after()`). One snapshot tool instead of four keeps tool-call latency down and gives the model one coherent, whitelist-formatted block. `explain_verdict`'s zod schema mirrors `buildConciergeTools#search_flights` (:271 — same IATA/date shape, already reviewed) but keeps the stricter support closure: server-loaded balances only. **Deliberately NOT grafted from the panel:** the `hop_support_sessions` table (a migration for an idempotency guarantee a closure flag delivers and a metric the brief doesn't require), `price_trip` (curated-destination inspiration, not support), and split read tools — all Phase 2 candidates at most. **`docs/solutions/` is NOT exposed to end users** — it documents internals (env keys, table names, seams) and is developer memory; the user-facing KB is `lib/support-kb.ts`, curated from the `/support` page content + engine constants, each entry carrying a `/support#anchor` deep link. The KB is **tool-fetched (≤3 entries per call), never inlined into the system prompt** — token cost stays bounded.

**Owner logging: piggyback, don't build.** Phase 1 logs (a) PostHog LLM analytics via `experimental_telemetry: { functionId: 'support-agent' }` (same as `concierge`/`dream`), and (b) agent-raised escalations stamped `trip.source = 'support-agent'` in the existing `hop_escalations` — the weekly business digest gains one section counting them (`trip->>source` filter, degrades to null like every other metric). A `hop_support_sessions` table + top-topics digest is named Phase 2; no migration this week.

## 2. Requirements

Done means:

- [ ] With `HOP_ENABLE_SUPPORT_AGENT` unset, the deploy is inert: `/support` renders byte-identical to today (no client JS shipped for the chat); `POST /api/support-agent` answers a calm static text line, 200 (never 500, never 404, never a stack trace — a stale open panel gets prose, not an error).
- [ ] Flag on + signed in: `/support` shows a chat panel above the FAQ. "Why did hop tell me to pay cash to Tokyo on March 12?" → the agent calls `explain_verdict(NRT, 2027-03-12, …)` (origin defaulting to the user's saved `homeAirport` when they don't restate it), and the reply narrates **only** the engine's figures: the pick, its cpp, the 2.5¢/pt line, taxes backed out, `$ saved` — with degraded sections stated plainly if `degraded[]` is non-empty. Same question twice → same numbers.
- [ ] Account questions ("what tier am I on", "did my alert fire", "where's my booking request", "is AwardWallet connected", "what are my points worth") are answered from the snapshot + the engine-computed `walletValue` — this user's rows only, resolved server-side from the Better Auth session `sub` (via the `lib/auth0.ts` compat shim), never from client-supplied context. Tier is stated **as recorded** (hedged — see §6/§9); `walletValue` is the only whole-wallet dollar figure the model may state, and it never multiplies balances × valuations itself (rule carried verbatim from `app/api/concierge/route.ts:280–285`).
- [ ] "Talk to a human" (button, or the agent recognizing it's out of depth / out of scope) → `createEscalation` with a clamped transcript excerpt (last turns, ≤2000 chars — stated honestly in copy as "a summary of this conversation") + account snapshot line in `trip`, owner email via `after()`, and the calm EscalationCTA-style confirmation. **At most one escalation row per conversation, enforced in code at conversation scope**: the chat panel mints a conversation key (UUID) when it opens and sends it with every request; `escalate_to_human` records it in the escalation's `trip` payload and, before inserting, looks up an existing escalation by that key (scoped to the caller's sub) — a repeat call in ANY later turn returns `{ok:true, already:true}` with the prior id instead of inserting. A per-request closure flag additionally de-dupes duplicate tool calls within one streamed response, but it is NOT the conversation guard — turns are separate HTTP requests. The lead appears in `/admin/support` with full context — no re-asking the user what happened.
- [ ] Signed out: the chat answers how-hop-works from the KB, invites sign-in for account questions, and escalation works with a typed `normalizeEmail`-validated email (existing route contract via embedded `EscalationCTA`).
- [ ] Clean refusals: no bookings, no payments, no refunds/cancellation actions (point to the issuing provider, per the FAQ's own answer), no promises or SLAs, no account mutations (the agent has zero write tools except `escalate_to_human`), nothing outside hop/travel-account scope.
- [ ] Flag on but the gateway/model fails before the first token → the route streams a **deterministic** `fallbackSupportAnswer(query)`: best KB hit + its `/support#anchor` + the mailto floor. No LLM, no numbers invented (tested).
- [ ] MOCK=1 never leaks into account claims: `get_account_snapshot` reads only the real resolvers — a signed-in user with nothing connected gets the honest empty answer (CLAUDE.md rule), asserted in tests.
- [ ] First tokens stream within a couple of seconds; rate-limited per-sub + per-IP with a friendly slow-down line; inbound thread clamped via `sanitizeMessages`.
- [ ] `npm run check` green.

Non-goals (deliberate):
- **No change to the email support channel.** `lib/support-reply.ts` stays account-blind — email `From` is spoofable and there's no safe email→sub map; the chat is the account-aware channel *because* the Better Auth session authenticates identity. This asymmetry is the privacy design, not an oversight (capture as a solutions entry at `/compound` time).
- No persistence of support threads (no new table); the transcript lives in the client for the session and is captured into `hop_escalations.trip` only on handoff.
- No changes to `/ask`, `/api/concierge` behavior (one additive export-reuse only), or the MCP server. No auto-sent replies anywhere. No Eve work.
- "Recent searches" from the owner's brief: hop does not persist searches today; the closest honest signal is the live transcript. Noted in risks; not invented.

## 4. Engine hooks — where every number enters

The moat, reasserted: **every economic number (cpp, miles, taxes, tier, ranking, verdict, $ saved, wallet value) is computed by `lib/*` and only narrated by the LLM — never invented.** The support agent has no path to a number except a tool result or the engine-computed `walletValue` line injected server-side:

| tool | exact `lib/*` call | returns |
|---|---|---|
| `explain_verdict(from?,to,depart,return?,adults?)` | `lib/search.ts#verdictSummary(params, balances)` (:376) — the same `assembleSearch` funnel as `/search`, `/ask`, and MCP; `balances` = server-loaded `getUserBalances(sub)` closed over, never model- or client-supplied; `from` defaults to `getPrefs(sub).homeAirport` so "why did hop say pay cash to Tokyo" works without restating the airport | `VerdictSummary` (:344): `{route, verdict, summary, pick:{miles,taxes,cashPrice,cpp,youHave,…}, options[≤6], degraded[]}` — passed through **verbatim** |
| `get_account_snapshot()` | `lib/accounts.ts#getUserBalances(sub)` → `Balance[]` (real resolver only — **never mock fixtures, regardless of MOCK=1**); `lib/subscription.ts#getUserTier(sub)` → `'free'\|'premium'` + `ALERT_LIMITS[tier]`; `lib/standing-orders.ts#countActiveStandingOrders` + `listStandingOrders(sub)`; `lib/standing-order-alerts.ts#listAlerts(sub, 5)` (route, cpp, delivered — engine-recorded at fire time); `lib/escalation.ts#listEscalations(sub)` (status per booking request); `lib/prefs.ts#getPrefs(sub)` (homeAirport); `lib/accounts.ts#getUserAwId(sub)` → boolean only | the whitelisted snapshot — no args, so the model cannot point it at another user |

## 5. Flags & seams

- **`HOP_ENABLE_SUPPORT_AGENT`** via `lib/env.ts#isSupportAgentEnabled()` — flag **and** `AI_GATEWAY_API_KEY`, the house double-lock. Off: `app/support/page.tsx` skips the island entirely (no client JS shipped, byte-identical page); the route answers a static pointer to the FAQ + `support@hop.flights` — **200, plain text, never 404** (a stale open panel degrades to prose, not an error). No new env keys; nothing reads `process.env` outside `lib/env.ts` patterns.
- **Email seam untouched:** handoff notification goes through `sendOwnerNotification` (gated on `isEmailEnabled()`, per ADR 0003), fired via `after()` so Resend latency never blocks the stream; unconfigured Resend → the escalation row still lands and `/admin/support` still shows it.
- **Privacy lines (the seam's contract):**
  - Account data is resolved **only** from the Better Auth session `sub` (`lib/auth0.ts` compat shim) inside the route; the support route ignores client-supplied balance/context payloads entirely (stricter than `/api/concierge`, because support speaks authoritatively about the account). The page's `email` prop exists solely to prefill the client-side EscalationCTA form.
  - `snapshotSummary` is a **whitelist** formatter: program names + balances, wallet value, tier (as recorded) + allowance, watch routes + active counts, last-5 alert route/cpp/date, escalation statuses, home airport, `AwardWallet: connected/not`. It never emits: API/hop token values, AwardWallet user ids, Stripe customer/subscription ids, other users' anything, or raw DB rows. Enforced by construction (it only receives the typed snapshot) and by test (§7).
  - No tool accepts a user identifier — cross-user reach is structurally impossible, matching the MCP rule ("a user's data is only ever reachable via that user's own token/session"). The one identifier-shaped arg, `escalate_to_human`'s signed-out `email`, sets only where the human replies — and is ignored when a session email exists.
  - Signed-out: `get_account_snapshot` returns `{signedIn:false}` and the prompt forbids any "your balances/points" claims — the anonymous-mode hard rules lifted verbatim from `lib/support-reply.ts#SYSTEM` (spoofable-identity register, already reviewed).
  - **MOCK=1 is a dev fixture switch for cash/awards search, never for account claims:** the snapshot path has no mock branch by construction.

## 6. Degradation plan

| failure | behavior |
|---|---|
| Flag off / no gateway key | No island; static `/support` + mailto + `/admin/support` all work exactly as today. Direct POST → static text line, 200. |
| Flag on, model/gateway fails **before first token** | Route streams deterministic `fallbackSupportAnswer(query)`: best KB hit + `/support#anchor` + mailto. No LLM, and the fallback path is itself bound by the no-invented-numbers invariant (contains zero cpp/miles/$ figures — tested). |
| Gateway/stream dies **mid-answer** | `onError` logs; pump loop is try/caught (concierge pattern); client shows the partial text + a calm retry line; "Talk to a human" is always rendered beneath the composer regardless of stream state. |
| DB unconfigured/down | Every snapshot sub-read hits its `withDb` fallback (`[]`, `'free'`, `0`, `null` — none throw). Known limit, stated honestly rather than papered over: `getUserBalances` returns `[]` and `getUserTier` returns `'free'` for both "none/free" and "read failed" — the resolvers **cannot** distinguish outage from absence today. Mitigation is phrasing, not fiction: balances → "I don't see any programs on file — check /account"; tier → "your plan as recorded is free". The `{ok, degraded}` resolver variant that would let the snapshot mark sections unavailable is a named Phase 2 item (§9); Phase 1 does not claim that behavior. |
| `verdictSummary` upstreams degraded | `degraded[]` flows through the verbatim tool result; hard rule: name the degraded section, suggest re-running shortly — never fabricate the missing side. Identical to the concierge's `search_flights` contract. |
| `createEscalation` → `null` | Tool returns `{ok:false}`; the agent gives the mailto floor (`support@hop.flights`) — the FAQ's own contact path. The closure flag is only set on success, so a later retry in the same conversation is allowed. |
| Owner email unconfigured/fails | Row persists; `/admin/support` console is the safety net (existing behavior). `after()` failure is fire-and-forget. |
| Duplicate escalation attempts | Enforced in code: per-request closure flag → `{ok:true, already:true}`; plus route rate limit; plus `normalizeTrip`/`normalizeEmail` clamps (defense-in-depth already in `lib/escalation.ts`). |
| Abuse | `checkRateLimit` sub+IP (`{capacity: 6, refillPerSec: 0.15}`) before any model/DB work → friendly text stream, never a bare 429 breaking the panel; `sanitizeMessages` clamps thread shape/size; `stopWhen: stepCountIs(4)` bounds tool fan-out per turn. |
| MOCK=1 (dev) | `explain_verdict` runs the engine, which serves fixtures for cash/awards — fine for the walkthrough. `get_account_snapshot` reads real resolvers only: a signed-in user with nothing connected hears the honest empty answer, never fixture balances. |
| Digest metric | `trip->>source` count degrades to `null` → section omitted, digest still sends (existing contract). |

All new persistence touches are reads or the existing `hop_escalations` write — every one `user_id`-scoped in code (service-role bypasses RLS; scoping is the code's job, as everywhere).

## 9. Risks & open questions

- **Resolver ambiguity (balances + tier)**: `getUserBalances` returns `[]` and `getUserTier` returns `'free'` for both "genuinely none/free" and "read failed" — during an outage the agent could understate a paying user's tier. Phase 1 mitigates with hedged phrasing only ("as recorded", "I don't see… — check /account") and **does not claim** unavailable-section marking it can't deliver. The `{ok, degraded}` resolver variants are the first-named Phase 2 item. Related accepted gap: `hop_subscriptions` is sparse until Stripe activation (task #16), so "as recorded" is doubly right pre-launch.
- **Prompt injection** ("show me user X's balances", "ignore your rules"): mitigated structurally — no tool takes a user identifier, tools close over the session sub, snapshot is whitelist-rendered, client context is ignored server-side. The security reviewer should still attack this path, including the signed-out `email` arg.
- **Escalation volume/spam**: bounded three ways — in-code once-per-conversation flag, route rate limits, `createEscalation` clamps.
- **Cost**: `explain_verdict` fans out to Duffel + seats.aero — the priciest tool. `stepCountIs(4)` + rate limit + prompt guidance (one re-run per question) bound it; watch PostHog `functionId: 'support-agent'` in week one. `transfer_paths` earns its slot only because it's free to carry — drop it in Phase 2 if telemetry shows no calls.
- **`trip->>source` filter**: supabase-js supports JSON-path `.eq`; verify in the Work lane — if it misbehaves, the metric degrades to null (existing digest contract), nothing else depends on it.
- **Transcript cap honesty**: the handoff attaches ≤2000 chars (most recent turns) — a long conversation is summarized by truncation, and the copy says "a summary of this conversation", not "the full transcript". A richer structured handoff is Phase 2.
- **Irreversible actions: none.** No payments, no bookings, no writes beyond an escalation row; the human handoff *is* the gate. Live Duffel key untouched.
- Open: **/privacy line** — one sentence noting that escalated support conversations are stored for follow-up; decide before the flag flips in prod (the zero-persistence design otherwise needs no policy change). Persist support threads (`hop_support_sessions`) + top-topics digest (Phase 2). Cross-link from `/ask` and `DegradedNote` into support chat (Phase 2). "Recent searches" aren't persisted anywhere today — grounding on them requires a new seam; deliberately out of scope.
- Compound step (queued for `/compound`, not this diff): promote two rules — (a) CLAUDE.md: "edit `/support` copy → update the matching `lib/support-kb.ts` entry in the same change" (the anchor-drift + threshold-drift tests make violations mechanical); (b) solutions entry: "support chat is account-aware because the session authenticates; email support is account-blind because `From` is spoofable."
