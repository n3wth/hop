# Eve — hop's proactive travel agent

> Design doc. Status: proposal. Author surface: `docs/plans/`.
> Grounded against [vercel.com/eve](https://vercel.com/eve) + Vercel docs (Eve, Workflows,
> AI Gateway, Sandbox, Connect) and a full pass over hop's current code.

## TL;DR

hop already owns the hard part — a deterministic points-vs-cash **verdict engine**
(`lib/search.ts#assembleSearch`) and two-thirds of a proactive loop (standing orders
*detect + record*). What it lacks is a **runtime** that runs on its own, a **channel** to
reach the user, and a **memory** that personalizes over time. [Vercel Eve](https://vercel.com/eve)
— "Next.js for agents": durable sessions, `schedules/`, `channels/`, `defineState`,
subagents — supplies exactly those three missing pieces. Eve becomes the *legs*; hop's
`lib/*` stays the *brain*. The engine still computes every number; Eve's LLM only narrates
and delivers.

---

## Concept overview

**Eve is hop's always-on travel agent.** Today hop is reactive: the user opens `/ask` or
`/search` and pulls a verdict. Eve flips that — it runs hop's own deterministic engine on a
schedule against each user's real balances and learned travel patterns, detects when a
redemption crosses the user's value line (`cpp ≥ 2.5`), and *pushes* the result to wherever
the user lives (email first, then web thread, then Slack/Discord). It is durable (sessions
checkpoint and resume), conversational (the user can reply "watch SFO→NRT business above
4cpp" or "stop showing me Tokyo"), and personalizing (feedback and Gmail-derived patterns
tune what surfaces next). Crucially, Eve preserves hop's core invariant — **every economic
figure is computed by `lib/*`, never generated by the model** — because Eve's tools wrap the
same engine functions the web app already calls.

---

## How Eve maps onto hop (the architecture)

Eve is **co-located in the hop repo** and deployed on Vercel alongside the Next.js app. Its
`tools/*.ts` import hop's `lib/*` engine directly — this is the *proven* path: the existing
standing-orders cron already imports `assembleSearch` + `getUserBalances` and runs the engine
headlessly with no user present (`app/api/cron/standing-orders/route.ts`). The external MCP
server (`app/api/[transport]/route.ts`, `hop_` Bearer tokens) stays as-is for *third-party*
agents ("Add to Claude"); Eve does not need it because it lives next to the engine.

| Eve primitive | hop seam it fills | Today |
|---|---|---|
| `schedules/` (`defineSchedule({cron, run})`) | the scheduled runner | one cron, `0 */6 * * *`, **gated off** (`STANDING_ORDERS_CRON_ENABLED` unset → 503) |
| `channels/` (Email, Web Chat, Slack, Discord, WhatsApp, Twilio) | **outbound delivery** | **none** — `PUSH DELIVERY TODO` no-op; `alerts.delivered` hardwired `false`; zero delivery deps in `package.json` |
| `defineState<T>("ns.key")` (durable typed per-user state) | learned patterns + feedback memory + dedupe ledger | single `last_notified_offer` fingerprint; `hop_conversations` is a latest-wins 40-turn blob |
| durable sessions + human-in-the-loop park/resume | "book it" approval gates | n/a (checkout flag-gated) |
| subagents (own context/session/state) | specialized scanners | n/a |
| AI Gateway | model calls | already used — concierge runs `anthropic/claude-sonnet-4-6` via gateway |

**Invariant preserved:** Eve tools return engine output (`assembleSearch`, `priceTrip`,
`cpp`/`tier`, `effectiveBalanceFor`); the model composes prose around those numbers. Same
rule as the concierge's `reconcileEconomics` — model numbers are ignored, engine numbers win.

## Workflows

Five concrete workflows, ranked by how little net-new infra each needs (ship order).

### 1. Standing-order delivery — "the verdict that watches," finally delivered
The smallest gap and the fastest real proactive message. Detection already works; Eve adds
the schedule, the delivery, and durable dedupe.
- **Trigger:** Eve `defineSchedule` replaces the gated cron (per-watch cadence, not one global 6h).
- **Run:** `listActiveStandingOrders()` → per watch `getUserBalances` + `assembleSearch` →
  `evaluateOrder()` (pure crossing rule) → on a crossing, `receive(channel, {message})` and
  flip `delivered`; `recordNotifiedOffer` + a `defineState` ledger for multi-offer dedupe.
- **Conversational:** user DMs "watch SFO→NRT business above 4cpp" → `parseStandingOrder` →
  `createStandingOrder`; manage pause/resume/remove in-channel.
- **hop hooks:** `listActiveStandingOrders`, `assembleSearch`, `evaluateOrder`, `recordAlert`,
  `recordNotifiedOffer`, `parseStandingOrder`, `createStandingOrder`.
- **Fix first:** delivery channel (blocker #1), dedupe ledger (#3), seat-stub (#9).

### 2. Proactive opportunity detection — "pattern → cpp alert"
The flagship "we learned you fly Tokyo 3×/year → here's a 4.1cpp window" workflow.
- **Trigger:** daily `defineSchedule` (e.g. `0 8 * * *`).
- **Run:** per user, load `getTravelHistory` (Gmail patterns) + `getUserBalances`. Build
  candidate routes from `TravelPatterns` (`usualMonths`, `favoriteRegions`) ∪
  `affordableWith(totalPoints)` ∪ `topValue(n)`. Price candidates (`priceTrip` / `assembleSearch`),
  threshold deterministically (`cpp ≥ POINTS_THRESHOLD_CPP`; tier green `≥3.0` = "best find"),
  dedupe via `defineState`, deliver the best 1–2.
- **hop hooks:** `getTravelHistory`, `derivePatterns`, `affordableWith`, `topValue`,
  `assembleSearch`, `priceTrip`, `cpp`/`tier`.
- **Phase note:** ships first on **balances + saved profile** (live, reliable); switches on
  Gmail patterns in phase 2 once that seam is verified (see Gmail section).

### 3. Trip-window planning — "you usually go in March; here's the play now"
Award space books early; surface the redemption path before the user thinks to look.
- **Trigger:** schedule + pattern-driven (fires when a `usualMonths` window for a favorite
  region is ~60–90 days out).
- **Run:** assemble the best path now, `runComparePrograms` across the user's programs, and
  compute the transfer play with `effectiveBalanceFor` / `transferRoutesTo` / `sourcePointsFor`
  — "transfer 60k Amex→ANA to unlock this." If space isn't open, offer to set a standing order
  (hands to workflow #1).
- **hop hooks:** travel patterns, `transfers` graph, `compare_programs`, `sweet-spots`.

### 4. Conversational concierge with memory + proactive follow-ups — Eve as the always-on `/ask`
Eve becomes the durable, multi-channel front of the concierge.
- Same grounding (`buildAgenticSystem`: balances, destinations, profile, patterns) and the same
  deterministic tools (`price_trip`, `get_weather`, `web_search`, `save_profile_fact`), but now
  with **durable sessions across web + Slack + email** and persistent `defineState` memory.
- Eve can **initiate**: a found opportunity lands as a new turn in the *same* thread (today only
  `onFinish` of a user-triggered stream can append).
- **Feedback loop:** "not interested in Tokyo" / "I prefer nonstop, window" → `save_profile_fact`
  → `travel_profile` → `applyPrefs` tunes future ranking. This closes the personalization loop.
- **hop hooks:** `buildAgenticSystem`, `concierge-tools`, `saveConversation` (proactive append),
  `travel-profile`, `applyPrefs`.

### 5. Transfer-bonus & expiry watch — "use it before you lose it" *(phase 2, lower confidence)*
Monitor transfer-bonus windows and balance staleness; when a bonus makes a known sweet spot
reachable, surface it.
- **hop hooks:** `transfers`, `getUserBalances`, `sweet-spots`, `destinations`.
- **Blocked on:** a live transfer-bonus data feed — none exists today (the card map is a static
  `TOP_CARD_BY_PROGRAM`; WS2 affiliates unbuilt). Defer until a source lands.

## How Eve learns / personalizes

Three signals, in descending order of reliability *today*:

1. **Real balances + saved profile (live now).** `getUserBalances` (manual + AwardWallet) and
   `travel_profile` (written by `save_profile_fact`) are working and trustworthy. Phase-1
   personalization runs entirely on these.
2. **User feedback (built, just needs the loop).** Every reply Eve gets is signal. "Stop
   showing Tokyo," "I fly business only," "window seat" → `save_profile_fact` → `applyPrefs`.
   This is the highest-leverage signal because the user volunteers it.
3. **Gmail travel patterns (built, gated off — see below).** `TravelPatterns` (usual months,
   favorite regions, typical cabin, trips/year) is the richest signal but not yet reliable.
   Enrichment in phase 2.

**Browsing intent has no data source in the repo today** (no clickstream capture; PostHog is an
external MCP, not wired into hop). Treat it as out of scope for v1, or a later add behind a new
analytics data plane.

## Gmail scanning prerequisite: built, not running

**Direct answer: the feature is fully built and unit-tested for its pure parts, but it is
gated off and needs work before an autonomous agent can rely on it.** It is *not* a stub — the
whole chain exists: OAuth start/callback routes, a Gmail REST client, a pure parser
(`lib/gmail-parser.ts`), Supabase persistence that stores *only* trip facts + the refresh token
(`hop_travel_history`), a read path that derives `TravelPatterns` (`lib/travel-history.ts`), an
`/account` connect/sync/disconnect UI, and consumption inside the concierge prompt.

What must happen before Eve depends on it:
- **Flag + credentials.** `isGmailHistoryEnabled()` requires `HOP_ENABLE_GMAIL_HISTORY` **and**
  `GOOGLE_OAUTH_CLIENT_ID` + `GOOGLE_OAUTH_CLIENT_SECRET` — all unset.
- **Google verification (the long pole — start day 0).** `gmail.readonly` is a *restricted*
  scope: needs an OAuth consent screen, a registered redirect URI, and Google's security review
  before non-test users can connect. This is weeks of external calendar time.
- **Background refresh.** Sync only runs on the OAuth callback and the manual `/account` "Sync"
  button — nothing re-reads Gmail on a schedule, so patterns go stale. Eve owns a refresh schedule.
- **Extraction validation.** Heuristics are tested only on synthetic fixtures; `findDestination`
  matches the *first* 3-letter IATA-like token (a fare class can mis-resolve), and there's a hard
  50-message cap with no pagination. Validate on real mail before reasoning on it.
- **Not on MCP** (only the in-app concierge prompt reads patterns) — irrelevant under the
  co-located model, but note it if Eve ever runs out-of-process.
- **Security:** `google_refresh_token` is stored plaintext; the migration ships no RLS.

**Verdict:** do not block Eve's launch on Gmail. Ship phase 1 on balances + profile; switch
Gmail patterns on in phase 2 once verification clears and extraction is validated.

## Deployment model — hybrid, web-first, email-as-MVP-delivery

Eve is **channel-agnostic** (`receive(channel, …)` routes per the user's stored preference),
but the rollout sequence is deliberate:

- **Email first (MVP delivery).** The only channel that needs *zero* new client surface and
  reaches every user. AgentMail (available as an MCP channel in this environment) or Eve's
  native email channel carries proactive alerts. Needs sender identity + unsubscribe.
- **Web Chat (primary interactive surface).** Embed Eve at `/ask` via `useEveAgent` — a durable,
  proactive-capable thread that supersedes the current reactive concierge. This is where hop's
  design/copy bar is enforced, so it leads the interactive experience.
- **Slack / Discord (opt-in, phase 2).** The high-delight "your travel agent in your DMs"
  experience for power users. Native Eve channels; opt-in only.

Rationale: lead with **web + email** because web is where the brand bar lives and email is the
universal reach channel with no new surface; Slack/Discord are niche delight and follow once the
loop is proven.

## 30-day rollout

**Day 0 (kick off immediately):** start Google OAuth verification for `gmail.readonly` (the long
pole), and provision live `DUFFEL_API_KEY` + `SEATSAERO_API_KEY` (without them `assembleSearch`
degrades to cash-only/`none`).

### Phase 1 — Days 1–14: foundation + first proactive loop (email-first)
1. **Delivery + contact layer (blockers #1–#3).** New schema: notification preferences + contact
   address + opt-in per user; an outbox/event ledger for proactive turns and dedupe. Wire Eve's
   email channel (AgentMail).
2. **Stand up Eve in-repo.** `agent.ts` (model via AI Gateway, `anthropic/claude-sonnet-4-6` to
   match the concierge), `tools/` wrapping `lib/*` (verdict, price_trip, balances, standing-orders),
   `instructions.md` + a `skills/` playbook encoding the copy voice (`docs/design/copy-spec.md`).
3. **Ship Workflow #1 (standing-order delivery).** Replace the gated cron with an Eve schedule;
   deliver crossings by email; flip `delivered`; add the dedupe ledger. **First real proactive message.**
4. **Ship Workflow #2 on balances + profile** (not Gmail yet) as a weekly opportunity digest.

### Phase 2 — Days 15–30: personalization + multi-channel + conversational
5. **Bring Gmail live** (assuming verification cleared): background-refresh schedule + extraction
   validation. Enable pattern-driven Workflow #2 + Workflow #3 (trip-window).
6. **Web Chat surface** at `/ask` (`useEveAgent`): durable sessions + proactive follow-ups
   (Workflow #4) + the feedback→profile loop.
7. **Slack/Discord opt-in channel.**
8. **Human-in-the-loop "book it" gate** — only if `isCheckoutEnabled()`; session parks on the
   approval and resumes on confirm.
9. **Workflow #5 (transfer-bonus)** deferred pending a bonus data feed.

## Open blockers

Ordered by how hard they gate the design. Each cites the seam.

1. **No outbound delivery channel anywhere.** `PUSH DELIVERY TODO` no-op
   (`app/api/cron/standing-orders/route.ts:17`), `alerts.delivered` hardwired `false`, zero
   delivery deps in `package.json`. Eve's channels / AgentMail solve it but must be wired
   (sender identity, per-user address, unsubscribe). **This is the #1 dependency.**
2. **No user contact / channel-preference store.** No email/phone/Slack-ID/web-push columns on
   any `hop_*` table; Auth0 holds identity but no notification record. Needs a migration.
3. **No append/outbox event store for proactive turns.** `hop_conversations` is a latest-wins
   40-turn blob; dedupe is a single `last_notified_offer` fingerprint. Need a durable ledger
   (`defineState` and/or a new table).
4. **Scheduler is one gated 6h cron.** `vercel.json` has a single entry; the handler 503s unless
   `STANDING_ORDERS_CRON_ENABLED` is set. Eve schedules replace it — confirm Eve runtime cadence
   vs. Vercel cron minimum frequency.
5. **Gmail gated off + long-pole verification + stale + unvalidated.** See the Gmail section:
   flag/creds unset, restricted-scope Google review needed, no background refresh, extraction
   tested only on fixtures, plaintext token, no RLS.
6. **Browsing-intent signal has no data source.** No clickstream capture in-repo. Specify a data
   plane or drop from v1.
7. **`assembleSearch` needs live Duffel + Seats.aero keys.** Absent → `degraded:['cash','awards']`
   and verdict collapses to `none`/cash-only. Provision keys (or run `MOCK=1` in dev). State the
   degraded-path behavior explicitly in Eve's prose.
8. **`/deals` is static; sweet-spot figures are seed estimates** (`VERIFY_CAVEAT`). Any proactive
   "book this" must re-validate live via `assembleSearch` before surfacing.
9. **Seat-availability gate is a permanent stub.** `seatsAvailable()` returns `undefined`
   unconditionally (`lib/standing-orders-model.ts`); `FlightOption` carries no seat count, so a
   "needs N seats" watch fires on phantom availability until seat counts are threaded through
   `lib/seatsaero.ts`.
10. **Agent identity / action-authority undefined.** Decide what Eve may *do* vs. *suggest*. The
    concierge's only write tool is `save_profile_fact`. Co-located Eve imports `lib/*` with full
    authority; scope writes (create standing orders, deliver, book) deliberately and add an audit
    trail. (Out-of-process fallback: act as a user via `userIdForToken` + `hop_` token.)
11. **Security blast radius.** Plaintext `google_refresh_token`, no RLS (code-only `user_id`
    scoping via the service-role client). An always-on agent reading Gmail-derived data raises the
    bar — encrypt tokens and add RLS before turning Gmail on.
12. **Two unreconciled sweet-spot datasets.** `lib/destinations.ts` (35, backs the MCP
    `sweet_spots` tool + `/deals`) vs. `lib/sweet-spots.ts` (16, backs `/sweet-spots` SEO pages).
    Pick one source of truth so Eve doesn't surface different "sweet spots" by surface.
