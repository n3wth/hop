# Newsletter signup

> Plan. Status: proposal.

TL;DR: add a single email-capture form (footer + a `/ask` empty-state / landing moment) that
stores a lead in a new `hop_newsletter_signups` table, mirroring the existing
`hop_escalations` / `lib/escalation.ts` lead-capture pattern exactly — same `withDb` degradation,
same rate-limit-before-DB-work shape, same never-throw route contract. No ESP integration in this
phase; delivery is a manual export, so the whole feature is inert risk-wise (no new transactional
email, no new billing surface).

## 1. Requirements

Done means:

- [ ] A visitor (signed in or signed out) can submit an email address from a compact form and get
      an inline "you're in" confirmation, without a page navigation.
- [ ] The email is validated, deduped (re-submitting the same address is a no-op success, not an
      error or a duplicate row), and persisted server-side.
- [ ] Signed-in users who submit have the row tied to their `user_id` (consistent with
      `hop_escalations`); signed-out submissions store `user_id = NULL`.
- [ ] The endpoint is rate-limited per-IP (and per-user when signed in) before any DB write.
- [ ] The DB/email layer never throws: an unconfigured database degrades to a friendly
      "couldn't save that — try again" response, never a 500 or a crashed page.
- [ ] `npm run check` (lint + typecheck + test) passes; a new `lib/newsletter.test.ts` covers the
      pure validators and the degrade-gracefully contract offline (no real DB in CI).
- [ ] Copy matches `docs/design/copy-spec.md` voice: terse, no marketing slop ("Get the smarter
      way to book, in your inbox" — not "Never miss a deal!!").

Non-goals (deliberately out of scope for this phase):

- No ESP (Resend Broadcasts / Mailchimp / Loops) integration — this phase only captures and stores
  the lead. Sending an actual newsletter issue is a separate, later effort once there's a content
  cadence to justify it.
- No unsubscribe flow / preference center — nothing is sent yet, so there's nothing to unsubscribe
  from. Note this explicitly in the confirmation copy so it isn't overclaimed.
- No admin UI to browse signups (mirrors `hop_escalations`, which also has no admin UI yet — a
  `listRecentNewsletterSignups` export is enough for a manual SQL/CLI pull).
- No double opt-in / verification email in this phase (adds `isEmailEnabled()`-gated complexity
  for zero payoff while nothing is being sent yet).

## 3. Engine hooks

**None.** This feature carries no economic figures (cpp, miles, price, tier, ranking, verdict) —
it is pure lead capture, same as `lib/escalation.ts`. The engine-invariant rule ("every number is
computed by `lib/*`, never generated by an LLM") does not apply because no LLM and no number is in
this loop at all. Confirmed: no `assembleSearch`, no `cpp.ts`, no `accounts.ts` call anywhere in
this feature.

## 4. Flags & seams

- **No new flag.** Unlike `isCheckoutEnabled()`/`isEmailPasswordAuthEnabled()`, this feature has no
  dangerous or partially-built downstream effect to gate — it only writes a row. It ships live
  once merged, same as `hop_escalations` did.
- **No new env key.** No ESP integration this phase, so no `lib/env.ts` accessor is needed. If a
  future phase adds Resend Audiences or another ESP, that phase adds
  `HOP_ENABLE_NEWSLETTER_SEND` + an env key then, gated exactly like `isCheckoutEnabled()`
  (explicit flag AND a working credential) — do not pre-build that gate now with nothing behind
  it (YAGNI).
- **Owner notification is optional, not required.** `lib/escalation.ts`'s route fires
  `sendOwnerNotification` after every lead (already gated on `isEmailEnabled()`/`RESEND_API_KEY`,
  no code change needed). Reuse `sendOwnerNotification` as a fire-and-forget `after()` call in the
  new route for parity — it's free (existing gated function, already no-ops cleanly when
  unconfigured).

## 5. Degradation plan

- `createNewsletterSignup` wraps its insert in `withDb(null, ...)` exactly like
  `createEscalation` — an unconfigured `DATABASE_URL` (or any DB error) returns `null`, never
  throws.
- The route treats `null` as a soft failure: `{ ok: false, error: "We couldn't save that just
  now — try again in a bit." }` with a `503`, never a `500`.
- **Dedup, not error, on repeat submission.** Add a unique index on `email` (case-insensitive:
  store `email` lowercased) so a resubmit is an `upsert`/`onConflict` no-op that still returns
  `{ ok: true }` — a user re-clicking "join" after a slow network response should never see an
  error for something that already worked.
- **Scoping.** `user_id` is nullable (mirrors `hop_escalations.user_id`, which is `NULL` for
  signed-out visitors by design) — this is intentionally the one `hop_*` table where an
  unauthenticated row is expected and correct, not a scoping bug. `listRecentNewsletterSignups`
  takes no user filter (owner-only export, same shape as `listRecentEscalations`) and must only
  ever be called from a trusted server context (a script or an owner-gated route if one is added
  later) — never expose it to a per-user API.
- Client component (`NewsletterForm.tsx`) never assumes success from a non-2xx response; it reads
  `{ok}` and renders the inline error state hop already uses elsewhere (e.g. escalation's `/ask`
  error copy), no thrown exceptions surfaced to the user.

- `createNewsletterSignup`: returns `null` when the DB is unconfigured (no throw) — asserts the

- `createNewsletterSignup`: returns `null` for an invalid email without attempting any DB call.
- Route-level: not unit-tested directly (no existing precedent for testing route handlers in this

## 7. Copy & design notes

Per `docs/design/copy-spec.md`'s "Footer / utility (keep it a real tool)" section — plain,
one-line, no marketing slop:

- Label: `Get the smarter way to book, in your inbox.` (states the value, no exclamation point,
  no "never miss a deal")
- Input placeholder: `you@email.com`
- Button: `Join` (not "Subscribe Now!" or "Sign Up →")
- Success state (inline, replaces the form): `You're in.` — one line, no confetti copy. Since this
  phase sends nothing, do NOT imply a cadence ("Look out for our next issue") — say only that the
  address is saved.
- Error state: `Couldn't save that — try again.` (matches the existing escalation error tone)

Design: flat editorial, no shadow/gradient/glow on the input or button — same border/token
treatment as the existing footer's hairline row. Lives in `SiteFooter.tsx`'s brand column, below
the social icon row, inside the existing `max-w-[34ch]` column so it doesn't widen the footer.
Bunny stays out of this — it's a utility footer, not a warm moment (per copy-spec's "bunny
personality budget": logo + one warm moment per region, and the footer isn't that moment).

**Note:** `components/SiteFooter.tsx` shows uncommitted local changes in the user's working tree
(outside this worktree, which branched from `origin/main`). Before implementing, diff against the
user's actual current `SiteFooter.tsx` — the brand column's structure may have already shifted.

## 8. Risks & open questions

- **Email deliverability/reputation is out of scope this phase** (no sends happen), so there's no
  irreversible action here — nothing to human-gate, unlike checkout/booking.
- **Open question:** should the form also appear on `/ask`'s empty state or only the footer? The
  footer alone satisfies "add newsletter signup" literally and is the lowest-risk single surface;
  adding a second surface is a small follow-up once this pattern is proven, not a blocker to ship
  v1.
- **Open question:** case-sensitivity of the unique index — recommend lowercasing at write time
  (`email.toLowerCase()`) rather than a Postgres `citext` column, to avoid a schema/extension
  change; note this explicitly in the migration.
- **Risk:** duplicating `normalizeEmail` from `lib/escalation.ts` verbatim is a minor DRY
  violation. Alternative considered: export `normalizeEmail` from `lib/escalation.ts` and import it
  in `lib/newsletter.ts`. **Recommendation:** import/reuse rather than duplicate — flag this for
  the code-simplicity reviewer.

## 9. Review hooks

- **degradation-reviewer** — the new `lib/newsletter.ts` + route must return `{ok:false}`/fallbacks
  via `withDb` and never throw; this is the core contract being copied from `lib/escalation.ts`.
- **security-reviewer** — new unauthenticated write endpoint: confirm rate-limiting runs before any
  DB work, confirm `user_id` scoping logic (nullable-by-design, not a scoping bug), confirm no
  secrets/env keys are introduced carelessly.
- **copy-voice-reviewer** — the form label/button/success/error copy must hold the
  `docs/design/copy-spec.md` bar (no marketing slop, flat design, no shadow/gradient/glow).
- **nextjs16-reviewer** — the new route handler and any client-component form-submission pattern
  must match Next.js 16.2.9 + React 19 conventions (read `node_modules/next/dist/docs/` for route
  handler + Server Action guidance before deciding whether this is a `fetch`-from-client-component
  or a Server Action).
- **compound-engineering:review:code-simplicity-reviewer** — flag the `normalizeEmail` duplication
  question from §8 and confirm the table/route aren't over-built relative to "capture an email."

Engine-invariant-reviewer and eve-architecture-reviewer do not apply — no economic figures, no Eve
agent surface touched.
